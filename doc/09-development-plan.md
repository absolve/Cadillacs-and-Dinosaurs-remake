## 结论（TL;DR）

- **本阶段目标：把第 1 关（City in the Sea）从选人到打倒 Vice 完整跑通**，四人可选、单人优先，多人同屏放本阶段末尾或下一阶段。
- **实现顺序照搬 [07 的建议](./07-dev-reference.md#七建议的实现顺序)**，按依赖关系切成 7 个里程碑（M0~M6）：工程骨架 → 核心战斗 → 力量系统 → 移动扩展 + 抓取 → 必杀技 → 敌人 + 刷怪 + 前两段 → 演出 + Vice + 收尾。
- **力量（暴击）系统在 M2 就做**，它影响所有伤害计算，放后面会返工。
- **缺数据的部分全部走 `[推定]` 占位**（帧数、移速、敌人伤害、第 1 关时限等），占位值集中放在一张表里，方便日后实测替换。
- **不含原版素材**（版权约束，见 [doc/README](./README.md#版权)）：美术 / 音乐用占位资源，精灵尺寸与判定盒按 [08 §13](./08-rom-data-tables.md#13-精灵尺寸表用于设定判定盒与碰撞体) 搭建。

### 关卡加载策略（2026-11-06 拍板）：房间 = 数据驱动锁屏段

- **定义**：一个「房间」= 一个**锁屏段**，是**数据单元而非独立 `.tscn`**——
  由 `AreaData`（`size` / `walk_band(y_min,y_max)` / `vertical_scroll`）
  + 该段的刷怪记录（16 字节，含触发屏幕区间，如第 1 关 A 段 `920→1120`）
  + 锁组（`lock`，靠「已生成敌人数」计数器解锁，对应原版 `$FFB358`）
  + 背景切片引用 四样构成。
- **串接**：`StageDirector`（autoload 单例）按关卡数据把房间排成序列，随摄像机位置推进：
  玩家进触发线 → 摄像机锁屏 → 生成该房间敌人 → 清空 → 解锁推进下一段。
  原版 A 段是「连续卷轴 + 中途触发线」，因此**房间边界不卡死场景切换**，
  段落内滚动照常，只有 lock 组生效时才停摄像机。
- **加载粒度**：同一关的房间在**一个关卡根场景**内按需实例化，
  只保持**视野 ±1 房间**的敌人 / 道具 / 背景层活跃，出视野即释放；
  背景按 `sprite/backgrounds/` 现成的 256×256 分层 PNG 切片取用，
  第 3 关 12888 px、第 7 关 14320 px 纵向段靠这套流式加载扛住。
- **v1 落地情况（2026-11-06，「房间 + 背景」先行）**：`scene/stage/stage01/stage01.tscn` 已跑通——
  `StageBackground` 把 ROM 导出的**整条场景图**（实测并非 256 切片：`L1_S1_layer2 1792×512`、
  `L1_S2 1024×256`、`L1_S3 1024×1024`、`L1_S4 3840×512 + layer3`）1:1 平铺覆盖区域宽度、底边贴区域底；

  仍为 `[推定]` TODO[实测]：场景 S ↔ 区域 A/B/C 映射（现 1A←S1、1B←S2、1C←S4，S3 未接入待核对）、

## 演出慢放设计（2026-11-06 拍板）：节点级时间缩放

**问题**：击败敌人 / 玩家死亡时的街机慢放，不能用 `Engine.time_scale`——那会连 UI、BGM、摄像机一起变慢，还破坏「1 物理帧 = 1 逻辑帧」的确定性（无头断言全靠它）。

**方案**：**tick 门控 + `speed_scale`**，缩放限定整数步长 `{1, 2, 3, 4}`（= 每 N 物理帧推进 1 有效帧）：

| 层 | 载体 | 语义 |
| --- | --- | --- |
| `self_slow_step` | 每个 [FightObject] | 个体慢放（死者 / 凶手），有效帧计数 |
| `Game.world_step` | `autoload/game.gd`（全局信号 `dilation_changed`） | 全屏慢放（玩家死亡），按**真实物理帧**倒计时恢复 |

- 有效步长 = `self_step × world_step`；`FightObject._physics_process` 里累加器决定本物理帧是否推进，**不推进就跳过**：状态机（`StateMachine` 读宿主 `is_local_tick()`）、计时器（无敌 / 眩晕免疫 / `frames_in_state`）一起变慢；
- **位移天然减速**：`move_and_slide()` 每次有效 tick 仍走「1 真实帧的位移」，tick 率变成 1/N → 速度自动变 1/N，不用改 delta 口径；
- **动画同步**：`sprite.speed_scale = 1/N` 每物理帧刷新，动画与逻辑同缩放不脱拍；
- **摄像机 / 输入缓冲不进门控**，保持真实速率（画面流畅、输入不丢）；
- 触发接线：敌人被打死 → 死者 `(step 3, 18 有效帧)` + 凶手 `(step 3, 6 有效帧)` `[推定] TODO[实测]`；玩家死亡 → `Game.set_world_slow(4, 45 真实帧)` `[推定] TODO[实测]`。

**取舍**：被缩放的玩家操作会「变钝」——这正是街机慢放的意图。**否决**的替代：全面 delta-time 化（大返工、破坏帧计数纪律）；Godot 时间细分（粒度不可控、无法只慢人物）。

## 段内事件与剧情演出设计（2026-11-06 拍板）

**原则**（doc/05 §演出）：剧情不走独立引擎——**复用刷怪系统 + 对象姿态**，玩家进 `CUTSCENE` 状态冻结输入。

1. **数据**：`AreaData` 增 `events: Array[StageEvent]`（M5 后落地）。`StageEvent` = 触发条件（X 触发线 / 锁组清空 / 计数器）+ **串行动作列表**：
   `spawn_records`（刷「剧情对象」，用 `pose` 字节指定姿态）、`camera_focus`（摄像机移到区间并锁）、`player_state`（进 `CUTSCENE` / 沿脚本路线走 / 自动放招式）、`dialogue`（台词幕，复用 UI）、`wait_frames` / `wait_until`（简单等待条件）。
2. **运行时**：`StageDirector` 已有触发线与锁屏，事件检查只是同一循环的扩展；演出期间摄像机冻结复用 `locked`。
3. **玩家演出**：新增 `PlayerCutsceneState`：不读输入，可被脚本驱动移动与招式（「开场自动必杀清场」= 脚本调用 attack 状态而非模拟按键），统一出口恢复输入。
4. **剧情对象行为**：不写 AI。敌人状态树加一类 `ScriptedState`，按 `pose` ID 查动作表（对应 ROM 的 AI 字节），例：迅猛龙「被拴链站立 → 激怒追击 → 打倒变绿沿指定 X 走出画面」。
5. **分层**：关卡间对话过场归 `GameFlow` + `CutscenePlayer`（M6 顶层流程），**不进** StageEvent；段内演出只做上面这套。

**取舍**：M6 只做「串行动作列表 + 简单等待条件」，不做通用 DSL（if/else、并行分支）——不够用再加，防止过度设计拖垮 M6（风险表已列）。
